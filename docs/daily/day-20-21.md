# Days 20-21 Report - Developer Platform and Launch Readiness

Date: 2026-07-29

  usage controls, scheduler, production database, Render service, and Vercel
  application before implementation.
- Preserved all existing users, resources, runs, credentials, organizations,
  entitlements, and cloud configuration.

  applying it atomically to production.

  service, and charged no money.

## Day 20 built - developer platform

- Added cryptographically random `afk_live_` API keys that are shown once and
  stored only as SHA-256 hashes with safe prefixes and last-use timestamps.
- Added eight least-privilege scopes for agents, workflows, runs, usage,
  webhooks, and platform status.
- Added configurable 10-600 request-per-minute limits with an atomic database
  counter, consistent request IDs, and standard rate-limit response headers.
- Added a versioned `/api/v1` contract for listing agents and workflows,
  starting controlled runs, reading runs and usage, publishing test webhook
  events, and reading operational status.
- Reused organization execution policy and usage enforcement before any
  developer-initiated run can enter the durable queue.
- Added OpenAPI 3.1 JSON and copyable curl examples.
- Added durable webhook subscriptions, events, deliveries, exponential retry,
  bounded attempts, dead-letter handling, and manual retry.
- Added HMAC-SHA256 timestamp signatures, stable event IDs, public-HTTPS and
  DNS-rebinding protection, redirect blocking, a 10-second timeout, and hashed
  response bodies.
- Webhook signing secrets are derived from the protected server key, shown
  once, and stored only as hashes.
- Agent and workflow completion triggers now publish safe webhook outbox
  events in the same database transaction as the run status change.
- Added bounded, privacy-preserving API request audit records with HMAC-hashed
  IP addresses and no request bodies.
- Added the production Developer Platform page for key lifecycle, scopes,
  OpenAPI, webhook lifecycle, delivery history, retry, and request audit.

## Day 21 built - launch readiness

- Added a six-step guided launch path covering authentication, an agent, a
  workflow, cost guardrails, developer access, and recovery.
- Added public operational status for the API, database, and agent engine.
- Added weighted launch acceptance checks with critical failures separated
  from optional launch warnings.
- Added expiring, downloadable recovery snapshots with canonical SHA-256
  manifests and a 2 MB safety limit.
- Recovery exports contain configuration and ownership references but exclude
  credentials, signing secrets, API keys, SCIM tokens, document contents,
  conversation memory, and run inputs and outputs.
- Added non-destructive restore dry runs for format, schema, ownership, digest,
  resource counts, and sensitive-field checks.
- Added retention cleanup for expired snapshots, old rate windows, API audit
  records, webhook events, deliveries, and readiness history.
- Added the production Launch Readiness page for status, onboarding,
  acceptance, recovery download, recovery verification, and launch policy.
- Removed React Router after the release audit found no advisory-free v7
  version. The browser-only routing layer now uses Wouter, the dependency audit
  is clean, direct/protected routes work, and the main bundle is smaller.

## Issues found and fixed

- The local acceptance runner initially used the expired Railway engine URL.
  It now starts an isolated local engine and verifies the combined contract
  without any model execution.
- A cleanup assertion selected a nonexistent `id` from the one-row onboarding
  table. It now uses the table's `user_id` primary key and confirms complete
  cascade cleanup.
- A sequential rate-limit test crossed a minute boundary. The verifier now
  issues 11 concurrent requests and proves exactly 10 succeed while one is
  rejected, exercising the atomic counter under contention.
- Local webhook signing lacked the production-generated encryption key. The
  acceptance process now injects an ephemeral test-only key; production
  continues to use its protected Render key.
- The frontend audit exposed high-severity React Router advisories across both
  available upgrade and downgrade paths. Replacing the dependency removed all
  known production dependency vulnerabilities and reduced bundle size.

## Blockers and constraints

- Render's free instance sleeps after inactivity, so the first request after a
  quiet period may be delayed while the API and engine wake.
- Billing remains deliberately in sandbox mode because no payment provider,
  approved prices, or live webhook secret have been configured.
- Native SSO still requires a real identity-provider application and securely
  stored provider secret.
- The beta is production-capable but has not yet been validated by external
  customer traffic, connector-specific provider certifications, or a
  multi-region disaster-recovery exercise.
